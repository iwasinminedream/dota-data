# Dota 6997: what changed

The report was generated automatically on 2026-11-26. The draft of all changes (parts: 1) was written by Claude Sonnet 5.5; the check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access); the tables below were calculated without a model.

## Summary

### Highlights
- No technical platform changes. The client (`libclient.so`) did not change: functions, strings and exports are identical. In `libserver.so` the function count went from 221948 → 221947, the code became 448 bytes smaller, and the strings and exports are the same.
- There are no restrictions for custom games, no game mode checks (comparison with 15), no command or convar lists, no browser checks and no new denials in this update.
- The only substantive server change is a null pointer guard in the function `0x5cb2bc0`. It writes a debug message and, if the object is empty, substitutes the string `"none"`. This does not affect the Lua API or the behavior of custom games.

### For custom game developers

### Client (libclient.so)
No technical changes to the client.

### Server and engine
- **`0x5cb2bc0`** (called from `CDOTAPlayerController::vfunc#255` and also from `0x5ce0e10`).
  - Previously, when building the debug message, the field `[объект + 0x28]` was read without a check.
  - Now the code does `test rax, rax` and, if it is zero, takes the string `"none"`.
  - The message is output only if the check `0x3b9f5e0(..., 2)` passes, which looks like a log level check. `0x3b9eae0` is called with a format string.
  - Conclusion: this is a guard that protects logging from a crash, not a change in logic. Confidence is high (the code was read in full), but the meaning of the message itself cannot be determined from the code.
- **The other changed `libserver.so` functions** contain no other technical changes.

### Schema and protocols
No changes. There are no tracked files in the list of changes.

<details><summary>What was corrected in the draft during the check</summary>

- **The hash in `0x62d3560`**: the draft described it as a possible change in the registration or lookup of the class `info_player_start_badguys` and advised checking whether the entity is found. This was not confirmed. The hash was simply computed differently (the constants were rearranged), and the "missing" call is related to this recalculation. No conclusion about class registration can be drawn.
- **The kill handler `0x62e0000`**: the draft linked it to a possible change in side effects on kills and advised checking kill events. This was not confirmed. The missing "call" `0x6213ae0` is an address inside another function, not a separate call target. There are no new events or keys, so no advice on checking kill events is included in the report.
- **The function `0x69fd330`**: I could not confirm the draft's guess about a moved-out freelist. There is no point in analyzing it further.
- **Corrected in the verified part:** the wording about "fewer crash risks when calling a virtual function" was replaced with the accurate conclusion: protection of debug output.
