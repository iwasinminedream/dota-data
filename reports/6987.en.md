# Dota 6987: what changed

The report was generated automatically on 2026-11-20. The draft of all changes (parts: 1) was written by Claude Sonnet 5.5; the check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access); the tables below were calculated without a model.

## Summary

### Main points

- The only substantive technical change is in `libserver.so`: diagnostics and protection for the attack record pool. The server has a fixed pool (1024 records). If it is exhausted, the server now writes a message to the console and a dump of all records. Freeing a record has become idempotent.
- There are no new or changed game mode checks. There are also no new whitelists or blacklists, browser restrictions, or command flags.
- API, console variables, events, schema, `.proto`, scripts and Panorama did not change. The symbol export did not change either.

### ⚠ Restrictions and oddities

**Hard limit of the attack record pool (1024) and new diagnostics when it is exhausted (`libserver.so`).**

- **What.** An attack record is allocated by the function `AddNewAttackRecord`. The index of the free record (`m_unNextFreeIndex`) is located at offset `+0x49818`. If it is greater than `0x3ff`, the check `m_unNextFreeIndex < DOTA_PROJECTILES_ATTACK_RECORD_MAX` fires. The pool size is `0x400` records (the code shows a stride of `0x120` per record and 6 bytes of service data with the "busy" flag at `+0x4801c`).
- **What changed.**
  - Previously, when the pool was exhausted, only this check was called (the old block `0x50778fc`, 76 bytes). There was no other code in this branch.
  - Now, in the new block `0x5077b7c`, the same check comes first, followed by the output of the string `Ran out of free attack record indices.`
  - Then the server iterates over all 1024 records and prints for each `"%d: %s src:%s target:%s"`: the index, `valid` or `invalid` (the busy flag), and the names of the source and the target. The names are taken by handles, and if there is no entity, `<null>`.
  - After the dump, the code returns to the index check. If a record has been freed, allocation continues (jump to `0x5077be1`). If not, the check fires again.
- **Who it affects.** The server of any game, including custom games. The limit and the check existed before; only the dump is new. Allocation is called by attack and projectile paths. The calling functions include `CDOTABehaviorAttackPhase::vfunc#67`, `DamageImpact` and several more functions without names.
- **What this means.** A custom game or plugin that spawns a very large number of simultaneously living attacks or projectiles runs into the 1024 limit. When the pool is exhausted, a large dump of 1024 lines will now go into the log, so clutter in the server console is possible. The limit itself did not change.
- **Reliability.** High for the code and strings: the code was read in full. What exactly happens after the repeated check that fails again depends on the check handler (`0x3b9d050`). I did not analyze it.

**Protection against double freeing of an attack record (`libserver.so`, function `0x5077fe0`).**

- **What.** The function frees a record: it resets the flag `+0x4801c`, links the record to the head of the free list at `+0x49818` and writes the index to `+0x4801a`.
- **What changed.** A new check appeared at the start of the freeing. If the flag `+0x4801c` is already 0 (the record is already free), the function returns immediately. Previously, such a call would put the index at the head of the free list again and could loop or corrupt the list.
- **Where it is called from.** 11 places, including `CDOTABehaviorAttackPhase::vfunc#67`, `DamageImpact` and the handler for misses and damage to buildings.
- **Who it affects.** The server of any game.
- **What this means.** Freeing the same record twice no longer corrupts the list of free indices. This is a general robustness fix, not a restriction.
- **Reliability.** High based on the code. The purpose of the function is inferred from its work with the same offsets as in allocation. The data does not give the reason for the change (a specific bug).
