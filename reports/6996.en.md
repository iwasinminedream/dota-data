# Dota 6996: what changed

The report was generated automatically on 2026-11-25. Draft of all changes (parts: 1) — Claude Sonnet 5.5, verification against the source data and final version — Claude Sonnet 5.5 (read-only access); the tables below were calculated without a model.

## Summary

### Key points
- The technical changes boil down to one: a limit of 255 entries appeared in `CNetworkTransmitComponent::StateChanged` (libserver.so, 0x5cc57c0). If the queue of changed entity fields is already longer, a new entry is not added to it. The conclusion from the code is reliable. The practical effect is indirect; details are in the "⚠" section.
- libclient.so did not change: there are no changed, added or removed functions. The size and exports are the same.
- In libserver.so the code grew by 576 bytes, while the exports and strings did not change.
- There are no new game mode checks (`== 15`), command lists, convars or addresses, and no changes in the browser and HTML panels. There are also no new or changed flags of console variables and commands.

### ⚠ Limitations and oddities
**Limit of 255 entries in the network field change queue** (libserver.so, `CNetworkTransmitComponent::StateChanged`, 0x5cc57c0 versus 0x5cc5600)
- **What changed.** The handler walks the list of changed field offsets (`[r12+0x20]` is the count, `[r12+0x28]` is the array). For each offset, except for the special entry with type `0x27`, it adds an entry to the pool at address `[this+0xbe0]`. The pool consists of entries of 0x48 bytes, and the number of entries in it is stored in the word `[this+0xbf6]`.
  - In the old build the entry was always added: a call to 0x5cc4f00 with `esi=0xffff`, then a state copy by the function 0x54092c0.
  - In the new build, `movzx eax, word [rbx+0xbf6]; cmp ax, 0xff; jbe <добавить>` stands before the addition (addresses 0x5cc5a0f–0x5cc5a28). If there are already more than 0xff entries, the addition is skipped.
  - After the skip the loop continues as usual: `[this+0xbc4]` is updated and the virtual handler is called.
- **Which path is affected.** The addition block has been moved to a separate section (0x5cc5d00–0x5cc5d63). The check is also present on the path "entry `0x27`, duplicate not found" (jump to 0x5cc5a24).
- **Who is affected.** Only the server. The function is called through the wrapper 0x50fc690, and that one from 0x51de2b0, which mentions `m_vecAvailableHerosPerPlayerID`, `m_vecLockedHerosByPlayerID`, `m_vecDisabledRandomHerosByPlayerID` and `m_vecItemStockInfo`. Other network fields may also be affected. I did not collect the list of all callers. This is network replication, and the client is not affected.
- **What this means for custom games.** If a very large number of fields of one network entity are changed in a short time, entries beyond 255 will not make it into the queue. What exactly is lost because of this (the field delta or only the metadata) cannot be determined from the code. There is no actual test on a live build. This explains possible oddities when many fields of one entity change within a single tick.
- **Reliability.** The condition itself and the threshold 0xff are visible directly in the code, and they are confirmed. What is stored in `[this+0xbf6]` I inferred from usage: the word `+0x16` in the pool structure is incremented when an element is allocated, and in the old code `cmp word [0xbf6],0` checks for emptiness. This is an inference of medium reliability. The effect on the game is unclear.

<details><summary>What was corrected in the draft during verification</summary>

- **Conclusion about `StateChanged`.** The draft called the block "new logic for flushing or updating a network variable when skipping ticks" and wrote that this does not affect the API. This is wrong for two reasons:
  - The ring buffer of 10 slots (`mod 10`, `0x66666667`) already existed in the old version, and in the new one it was only rebuilt by the compiler.
  - The real change is the condition `[this+0xbf6] > 0xff`, which skips adding an entry. The draft did not notice it.
- **Counter calculation.** The same place says that "slots `+0xc4c…` are zeroed, and their sum is subtracted from `+0xc56`". The conclusion is correct, but it was in the old version as well.
- **Limitations.** The draft concluded "no limitations". It missed the 0xff limit.
