# Dota 6992: what changed

The report was generated automatically on 2026-11-23. The draft of all changes (parts: 1) was written by Claude Sonnet 5.5, and the check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access); the tables below were calculated without a model.

## Summary

### Highlights

- **New warning in the GC message handler (libclient.so and libserver.so).** The constructor of the protobuf message from the packet (`msgprotobuf.cpp`) for `gc_msg_src == 2` now writes the line `Message %s(%u) from %s claimed client_steam_id %s with gc_msg_src %d.` to the GC log if `client_steam_id` does not match the one already recorded. The message is not discarded. See the section "⚠ Limitations and oddities" for details.
- **The semantics for `gc_msg_src == 2` also changed.** Previously, the source and steam_id were written to the message only if the source had not been set yet (`+0x50 == 0`). Now, for the value 2, they are always overwritten.
- **Client: three equipment list functions on `C_DOTAPlayerController` and `C_DOTA_BaseNPC` now return immediately if vtable slot 42 (`+0x150`) of the global interface returns `true`.** What this object is cannot be determined from the code. There is no connection to the custom game mode (see the "Client" section for details).
- **API, console variables and commands, schema, `.proto`, scripts and Panorama did not change.** The size of both libraries is almost the same (code −512 bytes for the client and −640 for the server), the exports did not change.

### ⚠ Limitations and oddities

**`client_steam_id` check for GC messages (libclient.so `0x7e66e40`, libserver.so `0x6bfa580`)**

- **Where.** The constructor `CProtoBufMsg` from `IMsgNetPacket`. It is called by the packet parser `0x7e64f00` for the client. The new line is present in both libraries, and the code of the diff functions is the same.
- **What the new code does.**
  - Arguments: `edx` — `gc_msg_src`, `rcx` — `client_steam_id`, `r8d` — an extra field that is written to `+0x6c`.
  - If `gc_msg_src == 2`, and the message already has a source (`+0x50 != 0`) and the recorded steam_id (`+0x40`) differs from the one passed in, the function writes a warning.
  - The warning goes through `0x7e649c0` (a wrapper over the GC logger `GCHost::EmitBaseMessageV`). The steam id formats are `[M:%u:%u:%u]`/`[C:%u:%u]`, and the message type name is taken from `messagelist.cpp::GetMessage`. The constant `0x30` is a parameter of the logger call. What it means is not visible from the code.
  - After the log, execution continues to the same branch as in the case of a match. The values `+0x40`, `+0x50`, `+0x6c` and the flags `|= 0x224` are written. There is no rejection or dropping of the message in this function.
- **Behavior change.** In the old version, these fields were written only when `+0x50 == 0`. In the new one, when `gc_msg_src == 2`, they are overwritten even if the source was already set. For other values of `gc_msg_src` the behavior is the same as before.
- **Who it affects.** Client and server, all games. This is not specific to custom games: there are no comparisons with `m_iGameMode == 15`.
- **What this means.** Anyone who builds or forwards GC messages manually (GC emulation, proxies) will see a warning when the steam_id differs. There is no blocking in this code.
- **Reliability.**
  - The logic of the function was read from the disassembly, so "log only, no rejection" is a reliable conclusion.
  - What the value `gc_msg_src == 2` means and which calling functions pass it has not been established.
  - The main packet parsing path (`0x7e64f00`) passes `gc_msg_src = 0` and `client_steam_id = 0`, so the new branch is not triggered on it.

### Client (libclient.so)

**Network: GC messages.** Described in the "⚠" section.

**Equipment list on entities (`0x579cb50`, `0x579d030`, `0x57cca20`)**

- **What changed.** At the beginning of each function, after the existing check `[global]+0x58 != 0`, a call to the virtual method `+0x150` (slot 42) of the object from the global cell `0x98e7fb8` was added. If it returns `true`, the function exits without doing any work.
- **What the functions do.**
  - `0x579cb50` is called from `C_DOTAPlayerController::vfunc#114`. It rebuilds the array from `+0x1018/+0x1010/+0x1008` and recreates the entries with the keys `"model"`, `"skin"`, `"ItemData"`.
  - `0x579d030` is called from a function with the strings `"isRespawn"` and `"OverrideWearableClass"`. It removes from the array the last element whose identifier matched.
  - `0x57cca20` is called from `C_DOTA_BaseNPC::vfunc#16`. It adds an element to the array with the limit `<= 0x20`.
  - All of this is the entity's client-side equipment list (wearables).
- **What this means.**
  - When slot 42 returns `true`, the client does not update this list.
  - The same slot 42 is also called in `C_DOTAPlayerController::vfunc#114`. It was already there before the update, and the result of `true` sets the flag `+0xeec = 1`.
  - What the object in `0x98e7fb8` is and when the method returns `true` could not be determined from the code.
- **Reliability.**
  - It is certain that the call was added.
  - The meaning of the condition is unknown. There is no tie to custom games: these functions have no comparisons with mode 15, and they do not mention custom games.

### Server and engine

- There are no technical platform changes.
- The server side of the GC constructor changed in the same way as the client side (see "⚠").
- The other changed functions of libserver.so are rebuild artifacts, template instantiations, or game code.

### Schema and protocols

- There are no new or removed platform classes or fields.
- `.proto`, scripts and Panorama from the VPK did not change.

<details><summary>What was fixed in the draft during the check</summary>

- The conclusion "GC messages with a foreign steam_id are possibly discarded" was not confirmed. The code only writes a warning and then still writes the values.
- The draft did not notice that for `gc_msg_src == 2` the fields are now overwritten unconditionally. Previously, the write happened only when the source was empty.
- The draft stated that steam_id is always compared. The check happens only when `gc_msg_src == 2`, the source is already set, and the steam_id differs.
- The draft described the three client functions correctly. I added that slot 42 of the same object was already used in `C_DOTAPlayerController::vfunc#114`, and that the condition remains unknown.
