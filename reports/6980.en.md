# Dota 6980: what changed

The report was generated automatically on 2026-11-19. The draft of all changes (parts: 5) was written by Claude Sonnet 5.5. The check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access). The tables below were computed without a model.

## Summary

### Highlights

- **The Lua API changes in `api-changes.txt` are almost certainly an artifact of how `files/*.json` was built, not a game change.**
  - The raw dump of both builds contains both server classes (`CDOTA_BaseNPC_Hero`: line 24650 in the old dump, 24651 in the new one) and client classes (`C_DOTA_BaseNPC_Hero`: line 45295 in both). The lines differ by one because of a noise line, "LUA Memory usage warning".
  - The client methods that supposedly "were added" (`GetHeroFacetID`, `ShouldDisplayInWorldUIElements`, `SetMessage`) are also present in the old dump: 5 occurrences there and 5 in the new one.
  - The current `files/vscripts/api.json` and `enums.json` contain no server classes and no `DOTA_GAMERULES_STATE_INIT`, although this value is present in the new dump (lines 9336 and 46754).
  - Conclusion: "+217 / −1780 / enum −500" is a file generation failure, not an API change. This was checked by sampling these classes and methods; I did not find out why exactly the build lost the server data.
- **There is only one real change in native modifiers.** For `modifier_juggernaut_blade_fury`, the property `MODIFIER_PROPERTY_ATTACK_POTENCY` now returns `%scepter_attack_damage_pct% - 100` (in the dump and in the libserver and libclient code).
- **Juggernaut, Blade Fury.** The effect of attacks during the spin now depends on who the owner is: Juggernaut, Rubick or Morphling. Separate materials for Rubick and Morphling were added to the VPK.
- **Techies, Sticky Bomb.** The `countdown` value (`1.5` in KV) was read as an integer and converted to float. Now it is read as a float, and the duration of the `modifier_techies_sticky_bomb_countdown` modifier is no longer truncated. This is a real behavior fix.
- **Chaos Knight, Armageddon** (the innate "Ahead, Armageddon"). The shared code for attacks along the charge path and the call at the end of the formation are no longer executed while the owner has states with bits 5, 6, 47, 33. By `MODIFIER_STATE` indices these are STUNNED, HEXED, FEARED, OUT_OF_GAME.
- **Starforge.** This is an already existing item (recipe: Meteor Hammer + Ultimate Orb, 6000 gold). Its burn now has its own particle `particles/items5_fx/starforge_burn.vpcf` (plus `_detail` and `_glow` in the VPK). The second channel particle now fades out smoothly instead of being cut off instantly.
- **Dazzle.** The "Null ability found…" error logging in Nothl Projection and the `.cpp` path itself were removed. The mechanic itself, judging by the code, is still in place.
- **Everything else** is recompilation and inlining: dozens of functions with address shifts in tables, helper extraction and register changes. This also includes the handle-handling changes and the extracted lists.

### New properties and methods: what they do

There are no new Lua API methods, events, modifier properties or Panorama API in this build (see the first item of "Highlights"). What was changed and added:

- **`MODIFIER_PROPERTY_ATTACK_POTENCY`** (enum 413, Lua name `GetModifierPropertyAttackPotency`) — changed.
  - **What it does.** This is the "item potency" for attacks: in the ability text, "These attacks deal X% damage and item potency".
  - **What changed.** The server slot `CDOTA_Modifier_Juggernaut_BladeFury::vfunc#128` and the client `vfunc#112` now perform `subss xmm0, [K:100]` before writing the result. It returns `field - 100` instead of the value itself.
  - **Check against KV.** `scepter_attack_damage_pct` = 0 (+75 with the scepter). It used to be +75, now it is −25, i.e. an effective 75% of the base.
  - **Conclusion.** The value is treated as a final percentage, and the property carries an offset relative to 100%. I did not reconstruct what exactly the engine does with the returned number; this is a conclusion from the formula and the text.
  - **For custom games.** `modifier_properties.json` gives `MODIFIER_PROPERTY_ATTACK_POTENCY: false`, and `enums.json` marks the property `broken: true`. The engine does not call the Lua function, so the property cannot be used from Lua.
  - **Reliability.** The code change — high. The meaning "potency as a percentage" — medium.
- **`CDOTA_Modifier_Item_MeteorHammer_Burn::GetEffectName`** (client, `0x4da9800`, 136 bytes).
  - **What it does.** A particle name callback. It takes the modifier's source item: if its name is `item_starforge`, it returns `particles/items5_fx/starforge_burn.vpcf`, otherwise the old `particles/items4_fx/meteor_hammer_spell_debuff.vpcf`.
  - **What it was before.** It used to be a trivial 8-byte function with a single particle.
  - **For custom games.** This is a native modifier, not accessible from Lua.
  - **Reliability.** High, the code was read in full.

### For custom game developers

- **Do not trust the current `files/vscripts/api.json` and `enums.json` for this version.** They lack the server classes (`CBaseEntity`, `CDOTA_BaseNPC`, `CDOTA_Ability_Lua`, `CDOTAGameRules`, etc.) and the server enums (`DOTA_GameState`, `DOTAMinimapEvent_t`, `DOTA_OVERHEAD_ALERT`, `EDOTA_ModifyGold_Reason`, etc.). They were not removed from the game (confirmed by the dump).
- **The client Lua API** (`C_BaseEntity`, `C_DOTA_BaseNPC`, `C_DOTA_Ability_Lua`, `C_DOTA_Item_Lua`, `C_DOTABaseAbility`, `C_DOTA_Item`, `C_DOTAPlayerController`, etc.) is not new in this build. Its types are simplified to `handle`, and it has no setters or actions.
- **Dumper noise** (`script_reload` +1/−1, `cl_script_reload` +26/−26): renumbering of `ACT_DOTA_*`, `ACT_DOTA_TORRENT` "appeared", `ACT_DOTA_LOADOUT_STATUE` "disappeared", `muerta_debut_satyr_a/b/c`, `radiant_melee_mars_shieldbash`. These are not game changes.
- **What may break an addon:** Blade Fury with the scepter — if the addon depends on potency (see above). Sticky Bomb — the timer is now 1.5 s instead of 1 s. Armageddon — the charge and attacks do not proceed while stunned, hexed, feared or out of the game. There are no other breaking API changes.

### Game code changes

11 functions were changed in libclient and 72 in libserver; 1 and 6 were added, 1 and 4 were removed. Few are significant; they are analyzed below. The rest is grouped at the end.

**Juggernaut, Blade Fury** (libserver)
- `vfunc#128` and the client `vfunc#112` — subtracting 100 from potency, see above. Reliability is high.
- `vfunc#97` now calls the new function `0x44b5ba0` (949 bytes) instead of the removed `0x44b5af0` (790). It creates the particle `juggernaut_blade_fury_attacks.vpcf` and attaches it to `attach_hitloc`.
- New in it: a query for the owner unit's name (virtual call `+0xe30`) and a comparison with `npc_dota_hero_juggernaut`, `npc_dota_hero_rubick`, `npc_dota_hero_morphling`.
  - For non-Juggernaut and unknown heroes, 0 is written to control point 10.
  - For Rubick — 1.
  - For Morphling — 2.
  - For Juggernaut himself, control point 2 = FLT_MAX is additionally set. Previously this was always done.
- I did not check what control point 10 does inside the particle itself. The link with the new materials `juggernaut_bladefury_attacks_rubick` and `_morphling` is a conclusion from the names. Reliability: code structure high, purpose of CP10 medium.

**Techies, Sticky Bomb** (`0x4d282e0`, called from `Techies_StickyBomb_Chase::OnDestroy` and `::vfunc#2`)
- It used to read an integer through another helper (`0x4d49130`) and `cvtsi2ss`. Now `countdown` is read as a float and goes straight into the `duration` of the `modifier_techies_sticky_bomb_countdown` modifier.
- If the ability is missing, 0 is substituted.
- KV: `countdown` = 1.5. Reliability is high.

**Chaos Knight, Armageddon** (the innate "Ahead, Armageddon"; KV `chaos_knight_armageddon`: `attack_while_charging` 1, `hit_radius` 150)
- In the shared helper `0x4ad26e0` (called from the `_Formation` and `_Charge` modifiers), after the check of virtual slot `0x538`, a read of the 64-bit flags `[+0x1248]` was added. With bits 5 (0x20), 6 (0x40), 47 (0x2f), 33 (0x21), the function exits.
- Then it looks for units in a radius and skips targets with bit 2 (ATTACK_IMMUNE by the same indexing). This is consistent with the interpretation "bit = `MODIFIER_STATE` index" (STUNNED, HEXED, FEARED, OUT_OF_GAME).
- `Formation::vfunc#2` (`0x4ad2a60`): bit 33 was added to the check of bit 0 (ROOTED). The call with `[+0x1af8]` and `[+0x1b10]` at the end is now behind the same set of conditions.
- `Charge::vfunc#2` (`0x4adf120`): checks of bit 0 and bit 33 were added; the timer decrement block `[+0x1b1c]` was merely moved.
- The bit → `MODIFIER_STATE` mapping is an assumption, indirectly supported by bit 2. Reliability is medium. The conclusion "they do not attack while stunned, hexed, feared and out of the game" follows from this mapping.

**Starforge** (`CDOTA_Item_Starforge::vfunc#335`, `0x4ebf890`)
- The function resets the channel particles `DOTA_Item.MeteorHammer.Channel` and `modifier_item_meteor_hammer_land`.
- For the second particle (`+0x938`), the `edx` argument in the call to `0x55284d0` was changed from 1 to 0.
- `0x55284d0` writes `edx` as a byte into the `CUserMsg_ParticleManager` message; by the standard signature this is "destroy immediately". Now the particle fades out smoothly, like the first one.
- The purpose of the flag is from the signature, not from a symbol. Reliability is medium.
- `GetEffectName` for the burn — see section 2.

**Puck, Coiled** (`OnIntervalThink`, `0x4563260`)
- The check "two units, then predicate `0x61d1a90`" was moved to the start. If it is true, the function exits immediately.
- Previously the call `0x6269c00` (with id 9 and `K:100`) was executed first, and only then the check. Now, when the predicate is true, this call is not made.
- What the predicate checks does not follow from the code. There is no visible change in mechanics. Reliability is low.

**Dazzle, Nothl Projection** (`0x48d1bd0`, called from `CDOTA_Ability_Dazzle_NothlProjection::vfunc#334`)
- The strings `CreateSoul`, `false` and two copies of `<NoAbilityName>` were removed (one remained).
- In `libserver.so`, the path `…/dota_unit_hero_dazzle.cpp` and the message "ERROR: *Dazzle: Nothl Projection - … Null ability found in index %d…" were removed.
- The cold fragment `0x48d1d4d` (38 bytes) was removed.
- The rest of the diff is register shuffling. The strings `shadow_wave_cdr`, `healing_amp`, `leash_start`, `base_leash_pull`, `leash_increase`, `modifier_dazzle_nothl_projection_soul_clone`, `dazzle_nothl_projection_end` are in place.
- Conclusion: the diagnostics of the ability swap error were removed, not the mechanic. What happened to the error branch (continue or something else) is unclear. Reliability is medium.

**Client**
- `0x5677270` (from `C_DOTA_BaseNPC::vfunc#155`, `CAdditionalWearable` and `C_DOTAWearableItem`; string `occlusion_glow`):
  - The result of the call `[vtbl+0xbd0]` is now saved and combined with a new call: if either of the two is true, it jumps.
  - A branch was added that compares the byte field `+0x557` (probably the team) with 3.
  - In the branch: a comparison of this field with the same field of another object, calls of slots `0x48`, `0x50`, `0x150`, a check of `[+0x58] == 3` on a global object.

- `0x5678766` (810 bytes): an emergency trap (`mov rax,[0]; ud2`) was added at the start, and `je F` was replaced with `je L`. The function compares `[+0x557]` with the argument. Most likely this is recompilation.

Looks like inlining.
