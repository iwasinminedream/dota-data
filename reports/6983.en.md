The report was generated automatically on 2026-11-19. The draft of all changes (parts: 4) was written by Claude Sonnet 5.5; the check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access). The tables below were calculated without a model.

## Summary

### Key points

- **This is a tiny update.** Build 6980 → 6983 (`SourceRevision` 11256062 → 11256873, 18 Nov 2026, 21:37:20). It is almost a hotfix: two `libserver.so` functions changed, five VPK assets (Chaos Knight particles and an Enchantress model) and `steam.inf`. The size, exports and `libserver.so` strings did not change.
- **The blocks "Lua API +1780 −217", "Lua Enums +500 −1" and "Native Modifier Functions ~61" in `api-changes.txt` are a comparison artifact, not game changes.**
  - The raw dumps `previous-dump.txt` and `dumper/dump` differ only in the version line, the `LUA Memory usage warning` line (it is simply located in a different place) and the values of `ACT_DOTA_*` constants/animation names in the client part. The server Lua API is identical.
  - Both dumps already contain both server classes (`CBaseEntity`, `CDOTA_BaseNPC`, `CEntities`, `GridNav` …) and client `C_*` (`C_BaseEntity`, `C_DOTA_BaseNPC`).
  - The same block in `files/changelogs/6980.json` starts on the same line 6 and extends to the same place ("Lua Enums" on line 19265), and `C_BaseEntity` is also listed there as "added". The block repeats from version to version.
- **The only possible logic change is the function `0x5c1a400` in `libserver.so`.** It is a handler for `CDOTA_BaseNPC::vfunc#512` with the debug string `"<NoAbilityName>"`. If the order object is in state 3, it is now moved to state 5 instead of being reset to "idle". The meaning of the states is not fully revealed by the code (details in section 4).
- **The function `0x5c19ae0` is a recompilation.** The "timer expired" check was expanded into a comparison of the time with a field; the logic stayed the same.
- **Visual tweaks.** The ultimate charge particles of Chaos Knight were updated (`chaos_knight_armageddon_ribbon_b` was added) as well as the Enchantress model (`enchantress.vmdl_c` and the texture `…_vmorf.vtex_c`).

### Changes in game code

2 functions changed in `libserver.so` (221833 in total, none added or removed).

**1. `0x5c19ae0` (2314 → 2330 bytes).**
- **What it is.** One of the states of the unit's order state machine: the dispatcher `0x5c1d600` uses the field `[order+0x40]` to call `0x5c1c360` for the value 1, `0x5c19ae0` for 2 and `0x5c1d1b0` for 3.
  - The function works with an ability cast order: it reads the ability name `[ability+0x840]`.
  - It checks the range (`0x61d45f0`), calculates the cast time (`vfunc#274/#270`) and at the end sets `[order+0x40] = 3`.
  - The neighboring `0x5c1c360` contains the strings `"npc_dota_hero_razor"` and `"modifier_disable_taunt_animation_cancel"`. `0x5c19ae0` itself has no strings.
- **What changed.**
  - Before: `lea rdi,[r15+0x48]; call 0x511bc30; test al,al; je → выход`.
  - Now: `call 0x56083c0` (current game time, float), then a comparison with `[r15+0x54]` and an exit on "less than or equal".
- **Why this is not a logic change.** `0x511bc30` is the same code as `IsElapsed`, in the form of a function. It calls `0x56083c0`, compares the result with `[timer+0xc]`, that is, with `[r15+0x54]`, and returns `ja` or `je`. The compiler simply reassembled the former check of `[r15+0x54] > 0` and `[r15+0x50] > 0`: it now comes after the time comparison.
- **Conclusion:** timer inlining, behavior unchanged. Reliability: high (I analyzed the disassembly of both sides).

**2. `0x5c1a400` (753 → 727 bytes, called from `CDOTA_BaseNPC::vfunc#512`).**
- **What it is.** The order handler for a no-target ability.
  - It writes the ability name to the log (when the `[rbx+0xa0]` flag is enabled) or defers the action to a queue if the `[rbx+0xa2]` flag is set.
  - The sibling `0x5c1aad0` (`vfunc#513`) does the same for a point target (a vector in `rdx`).
  - `vfunc#512` is shared by all NPCs: the name list includes `CDOTA_BaseNPC`, `CDOTA_Unit_Announcer`, `CDOTA_Unit_CustomGameAnnouncer` and 248 more classes.
  - What exactly the slot calls is visible only through `0x6228db0`, which walks the list from `[npc+0xc88]`. It is not named as a Lua callback.
- **What changed.**
  - Before, when there was no deferred path, `0x5cb3f70` was unconditionally called on `[rbx+0x10]`. This resets the object to state 0 (idle), returning control to the locomotor and zeroing the fields.
  - Now a check of `cmp dword [obj+8], 3` has been added. If the state equals 3, instead of the reset `0x5cb0b30` is called with an 8-byte payload from `[obj+0xc]`.
  - `0x5cb0b30` moves the object to state 5, transfers this payload there and sets `[owner+0x30] = 1`.
  - This same `0x5cb0b30` is already used in `0x5c1aad0` (when the cast time and backswing are positive).
- **Other changes in the diff.** The missing duplicate tail and the order of `test r12,r12` / `je` are compiler code rearrangement. There are now 12 direct calls instead of 15, but this is a consequence of the same rearrangement.
- **Gameplay meaning (assumption).**
  - Apparently, if the order is in state 3 at the moment a no-target ability is applied, it now moves to state 5 (essentially waiting for completion) instead of being interrupted. This way a no-target cast behaves the same as a point-target one.
  - What states 3 and 5 mean at the gameplay level cannot be determined unambiguously from the code.
  - Reliability: the logic change — high; the interpretation — low or medium.
- **KV and localization.** The function has no binding to specific values from KV (there are no constants from data in the diff).

The full list of functions is in `so-query.py funcs libserver.so`.
