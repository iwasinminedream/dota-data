# Dota 6976: what changed

This report was generated automatically on 2026-11-17. The draft of all changes (parts: 1) was written by Claude Sonnet 5.5. The check against the source data and the final version were done by Claude Sonnet 5.5 (read-only access). The tables below were calculated without a model.

## Summary

### Highlights

- **`SendToConsole` is restricted by a whitelist of prefixes (client and server).** Previously it executed any string. Now, for "ordinary" addons, the command is silently dropped if it contains `;` or a newline, or if it does not start with one of the predefined prefixes. This is the most noticeable change for custom games. It is visible only in the code (`libserver.so 0x3c9e5e0`, `libclient.so 0x3d9fce0`). Details are in sections 2 and 4.
- **The HTTP request logic did not change.** The "is the addon allowed" check before `CreateHTTPRequest` was already in the old build and remains the same. It has been moved into a separate function, which `SendToConsole` now also uses.
- **`CScriptHTTPRequest` and its 6 methods disappeared from the Lua API dump (−7).** The class registration code in the `.so` did not change, so this is most likely a dump artifact rather than an API removal. Details are in section 3.
- **There are no gameplay changes.** Heroes, items, abilities and units are not affected. There are no new Lua methods, events or Panorama APIs. In the game files, only `steam.inf` and one particle effect in the VPK changed.
- **The other changes in the `.so` files are recompilation.** These are register reallocation, shifted jump tables and constant folding of the schema name hash. The largest function, `DOTA_ExecuteOrders`, was rewritten by the compiler so heavily that no substantive changes in it can be isolated.
- **Build:** 6975 → 6976, SourceRevision 11236380 → 11246070, 12 Nov 2026 17:19 → 16 Nov 2026 16:28.

### New properties and methods: what they do

There are no new properties, events, methods, modifiers or Panorama APIs in the dump: `api-changes.txt` contains only 7 removed lines. The only new items are visible in the `.so` files.

**New entries in the `SendToConsole` whitelist**

Both libraries gained strings with a trailing space:
- `dota_camera_center_on_entity `
- `dota_camera_lerp_position `
- `dota_camera_set_position `
- `dota_creeps_no_spawning `
- `dota_enable_new_player_shop `

The commands themselves are not new. The old build already had `dota_camera_center_on_entity`, `dota_camera_lerp_position`, `dota_camera_set_position`, `dota_creeps_no_spawning`, `dota_enable_new_player_shop`, `+dota_camera_center_on_hero` and `inspectheroinworld` (verified with `strings old libclient.so`). Only the strings with a trailing space are new.

- **What the code does.** The function checks the prefix via `_V_StringAfterPrefixCaseSensitive` (case-sensitive). The trailing space is needed so that arguments follow the name.
- **What is visible in the prefix array.** An array of 8 pointers on the stack (`[rbp-0x60]…[rbp-0x20]`). Four elements are read as strings: `dota_camera_set_position `, `+dota_camera_center_on_hero`, `dota_enable_new_player_shop `, `inspectheroinworld`. The other four are loaded from data, and `so-query` does not reveal them. What exactly they contain is an inference from indirect evidence: the three other new strings have no direct references from code, which is consistent with this. The full contents of the list are not confirmed.
- **How to use it.** From a custom game, call through `SendToConsole` only commands with these prefixes, without `;` or a newline.
- **Reliability.**
  - High for the very fact of the whitelist and for the rejection conditions: the disassembler shows them.
  - Medium for the full contents of the list (4 of 8 are visible).
  - It is unclear what the "exception" checks the five values against (see section 4).

### For custom game developers

- **`SendToConsole(cmd)` may silently do nothing.**
  - Both server and client are affected (in the API it is `available: both`).
  - There is no error or message on rejection.
  - All calls such as `SendToConsole("dota_camera_distance 1500")`, `SendToConsole("dota_...; ...")` and any other commands outside the list are at risk.
  - The exception is addons for which the same check as in `CreateHTTPRequest` passes (section 4).
  - Check all uses of `SendToConsole` in your addon on 6976.
- **`SendToServerConsole` is not in the list of changed functions.** Based on the code diff it did not change, but I did not analyze it separately.
- **`CScriptHTTPRequest` disappeared from the dump together with its methods.** The methods are: `Send(callback)`, `SetHTTPRequestAbsoluteTimeoutMS(ms)`, `SetHTTPRequestGetOrPostParameter(name, value)`, `SetHTTPRequestHeaderValue(name, value)`, `SetHTTPRequestNetworkActivityTimeout(seconds)`, `SetHTTPRequestRawPostBody(contentType, body)`.
  - `CreateHTTPRequest` and `CreateHTTPRequestScriptVM` remain in the dump and return `handle`.
  - The string `CScriptHTTPRequest` remains in `libserver.so` and `libclient.so`. It is registered lazily, inside the request creation function (`0x51185f0`, called from `0x5119230` and `0x51194c0`). These functions did not change in logic.
  - Conclusion: a probable dump artifact. The class is registered only on the first request creation, so the dumper may not have seen it. Reliability is not high: it can only be definitively verified with a live run.
  - If your addon has HTTP code, test it on 6976.
- **Console variables.** There are no new ones. In the `so-diff` for `libserver.so`, the strings `+dota_camera_center_on_hero` and `-dota_camera_center_on_hero` are marked as "added". This is a parsing artifact: the string `+dota_camera_center_on_hero` was also in the old build.
- **Events, modifiers, Panorama, `HasFunction`.** No changes.
- **Possible false positive in the dump.** `dump-noise.md` describes noise in the `cl_script_reload` section: reordering of `ACT_DOTA_*` values and the addition of `ACT_DOTA_TORRENT`. This is dumper noise, not game changes, and it did not make it into `api-changes.txt`.

### Changes in game code

In `func-diff.txt`: `libclient.so` — 6 changed, 2 added, 1 removed; `libserver.so` — 92 changed, 2 added, 1 removed. There are three substantive logic changes: `SendToConsole` on the server and on the client, plus the extracted shared check.

**1. `SendToConsole`, server**
- Functions: `libserver.so 0x3c9e5e0` (new, 415 B); the old `0x3c9e4a0` (326 B) was removed.
- This is indeed `SendToConsole`: a pointer to it is stored next to the description `Send a string to the console as a client command` (reference from `0x3ce1b52`, function `0x3c9e5e0`).
- The old version took the string, checked for the presence of a console context and called `vtable+0x170`. There were no filters.
- The new version does the following:
  1. First, the same context checks.
  2. Then it calls `0x50fed30`. If it returned true, the command is executed without restrictions.
  3. Otherwise, `strchr(cmd, ';')`. If found, it returns without executing.
  4. Then `strchr(cmd, '\n')`, the same.
  5. Then it iterates over 8 prefixes via `_V_StringAfterPrefixCaseSensitive`. On a match, it executes; if there are no matches, it returns without executing.
- Reliability: high for the logic (disassembler), medium for the prefix contents.

**2. `SendToConsole`, client**
- Functions: `libclient.so 0x3d9fce0` (new, 299 B) instead of `0x3d9bb80` (40 B).
- The old function simply called `vtable+0x198` and executed any string.
- The new one is structured the same way as the server one: the `0x4f93210` check, then `strchr` for `;` and `\n`, then the prefixes.
- Execution goes through `vtable+0x198` with the same arguments as before.
- Reliability: high.

**3. Shared "exception" check (`0x50fed30` on the server, `0x4f93210` on the client)**
- The function reads [object]→+0x18→+0x210 and compares the value with five constants: `0x1bf920a7`, `0x255be816`, `0x1f03838e`, `0x1c3c5fb7`, `0x6031f2df`.
- If there is a match, it returns 1.
- What this value is (a hash of the addon ID, map or mode) cannot be determined from the code. All I can say is that it depends on the current addon/mode.
- This same check was previously inside `CreateHTTPRequest`: the comparison with `0x6031f2df` is present both in the old build and on the client.
- Reliability: high for the check itself, not established for the meaning of the constants.

**4. `CreateHTTPRequest` (`libserver.so 0x5119230`, called from `0x51194a0`; client-side `libclient.so 0x4f97b80`)**
- The parsing of the methods `GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `OPTIONS` did not change. The same five comparisons, the same lookup via `[rax+0x850]`.
- The lookup block was moved: it used to come right after the check, and now comes after the main branch. The duplicated `+0x18/+0x210` check in it is the same code.
- The change is a reordering of branches and the epilogue. Instructions: 143 → 147 on the server, 138 → 137 on the client.
- Reliability: high that the logic did not change.

**5. `0x3ce9f20` (`libserver.so`, 317 B, was 145)**
- A template script call "adapter". It takes two arguments (`ecx == 2`) and calls a native function.
- New: a variable type check on the byte `[r12+8]` was added (values `0x1e`, `2`, `0x4f`). For other types the value is converted into a temporary 0x200-byte buffer.
- It is called from both registration tables (`CVScriptGameSystem::vfunc#85` and `CDOTAVScriptGameSystem::vfunc#85`).
- Which exact Lua function is behind it could not be determined. The meaning is casting the argument type to a string/value. Reliability is low.

**6. `0x594dfe0` (`libserver.so`, `DOTA_ExecuteOrders`, `dota_execute_orders.cpp`, 28348 B)**
- Called from `CDOTA_Modifier_Lich_FrostArmor_Autocast::vfunc#126`, `CDOTA_Ability_Juggernaut_HealingWard::OnSpellStart`, `CDOTA_Ability_AntiMage_Mana_Overload::OnSpellStart`.
- The diff contains 7103 lines. I reviewed the beginning (about 800 lines): almost all of it is register reallocation (`r13` → `r15`, stack offsets). There is also block reordering: one call with code `0x65` moved to a different branch, and several element-count checks disappeared. The formal markers (`+0xffffffff +0xc +0x20 +0x3a +0xffff`, fields `+0x410 +0x24`) could not be tied to specific behavior.
- Conclusion: changes in order execution are possible, but are not proven by this diff. Reliability is low.

**7. `0x5122300` (`libserver.so`, the function with the string `<NoAbilityName>`)**
- A function that validates item/ability usage orders (called from `DOTA_ExecuteOrders` and 5 other places).
- The branch "if the virtual method of slot `0xed0` (474) is not overridden, read bit 5 of the byte `[[this+0x840]+0x2ae]`" was removed. Now `call [vtable+0xed0]` is always made.
- Labels such as `CDOTA_Item_BotChallenge_MeteorStaff::vfunc#474` in the output are just the shared address of the base implementation; they have nothing to do with the item.
- This is the compiler dropping automatic devirtualization. Behavior with the base implementation is the same. Reliability is medium.
