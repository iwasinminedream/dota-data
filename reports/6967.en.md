## Summary

### Highlights
- Game changes are visible only in the server library code, libserver.so: 7 changed functions and 1 added. In libclient.so, no function changed. There are no new strings or exported symbols in either library. The API changes file (api-changes.txt) is empty.
- **Meepo — MegaMeepo: the only logic change.** Previously, in three places (the MegaMeepo cast, the end of the `modifier_meepo_megameepo_self` effect, and one more unnamed ability callback), the internal list of clones "on the shoulders" was simply zeroed out. The code did nothing about `modifier_meepo_megameepo` on those clones. Now there is a common new function for this. It walks through the list, removes `modifier_meepo_megameepo` from each clone that still exists, frees the list's memory, and resets the second list. This appears to be a bug fix: a clone could remain with the MegaMeepo modifier after the form ended or after the ability was cast again. Confidence is high: the code was analyzed in full.
- The changes in the functions of Kez (Katana: strike with Aghanim's Shard), Legion Commander (Press the Attack), Muerta (registration of the network field `m_hDoubleShotTarget`) and in one utility function are a recompilation. The compiler inlined or outlined helper code differently, and the behavior remained the same.
- There are no changes in the Lua API, Panorama, events, modifiers or console variables.

### For custom game developers

- If your custom game has MegaMeepo, or your code relies on `modifier_meepo_megameepo` on clones, note that the game now removes it itself from all clones in the list when MegaMeepo ends or is cast again. If you applied this modifier manually and expected it to stay, it will now be removed. The conclusion is drawn from the code; it was not verified in-game.

### Game code changes
All changes are in libserver.so. All functions were analyzed (`so-query funcs libserver.so`).

**Meepo — MegaMeepo (logic change)**
- **New function 0x4a13270** (295 bytes, string `"modifier_meepo_megameepo"`, unnamed). It is called by three functions: `CDOTA_Ability_Meepo_MegaMeepo::vfunc#365`, `::OnSpellStart` and `CDOTA_Modifier_Meepo_MegaMeepo_Self::OnDestroy`. What it does:
  1. makes the same helper call as in the old code (0x5b86b40, formerly 0x5b86a80);
  2. walks through the list of clone handles (size in field +0x868, data in +0x870). For each entity that still exists (check of byte +0x5d1 == 3, the same as everywhere in the ability code) it calls 0x5f6c290 with `"modifier_meepo_megameepo"`. This is a wrapper over the unit's modifier manager (`this+0x1300`), with 484 callers, for example `Axe_One_Man_Army::OnUnStolen` and `Morphling_Replicate_Manager::OnDestroy`. Most likely, this is RemoveModifierByName;
  3. frees the list's memory (zeroes +0x870 and +0x878);
  4. zeroes +0x880.

  What the list +0x868/+0x870 is can be seen from `vfunc#371`: clones that received `modifier_meepo_megameepo` are added there (parameters `source_meepo`, `previous_meepo`, `meepo_count`). The list +0x880/+0x888 most likely stores clones in flight after being thrown (`modifier_meepo_flung`).
- **vfunc#365** (0x4a133a0, unnamed slot; which event it corresponds to is unknown). Before: remove `modifier_meepo_megameepo_self` from the owner, then the helper call and `[+0x868]=0`, `[+0x880]=0`. Now: remove `modifier_meepo_megameepo_self`, then a jump to the new function.
- **OnSpellStart** (0x4a65380). The zeroing of fields +0x868/+0x880 at the start of the cast was replaced with a call to the new function. The rest of the code did not change: searching for clones in the radius, exclusions for `modifier_faceless_void_chronosphere_freeze`, `modifier_enigma_black_hole_pull` and `modifier_legion_commander_duel`, the throw with `modifier_meepo_flung`.
- **CDOTA_Modifier_Meepo_MegaMeepo_Self::OnDestroy** (0x4a74f50). Likewise: after the clones are taken off the shoulders (0x4a12a10), the list is cleared by the new function rather than by direct zeroing.
- **What this means in the game.** Previously, when the list was reset, this code did not remove the modifier from the clones; now it does. This is almost certainly a fix for cases where a clone stayed in the MegaMeepo state. The localization tooltip ("The hero puts all clones within %radius% on their shoulders…") has nothing to do with this change. There are no numeric constants in the change. Confidence: for what the code does — high (all code of the new and old versions was read), for "bug fix" — medium (this is an interpretation).

**Recompilation (behavior unchanged)**
- **Kez, function 0x4a4b270** (katana strike with Aghanim's Shard: strings `backstab_angle`, `modifier_kez_katana_shard_debuff`, `kez_katana_impale.vpcf`). It is called by 0x4a5cf40 (`kez_switch_weapons`), which in turn is called by `CDOTA_Modifier_Kez_Katana::vfunc#95`. Previously the entity handle was computed directly in the code (bit operations `shr 0xf`, `and 0x7fff`, `shl 0xf`, `or`, value -1 for null). Now the handle-writing function 0x49aac50 is called, which this same code also calls for the second handle. The result is the same. The constants and the checks for backstab and duration did not change. Confidence is high.
- **Legion Commander — Press the Attack::OnSpellStart** (0x4a7bdb0). In both the old and the new code, the target and the caster are added to the list of units found in the radius only if they are not already there. Previously the addition was done by calling 0x4a6b7b0, now it is inlined into the code (hence the "+1" constants). There is no new check, contrary to the draft. Confidence is high.
- **Muerta, function 0x4aa7a30.** This is not Double Shot logic, but the static registration of the network field `CDOTA_Unit_Hero_Muerta::m_hDoubleShotTarget` in the schema. The inlined class name hashing (MurmurHash2 constants `0x5bd1e995`, `0x6174`, `0xd`, `0xf`) was replaced with a call to 0x3a3fc80. It does not affect the game. Confidence is high.
- **Function 0x5c25d70 (utility).** Its "new" first 80 bytes (the check of `[rdi+0x61]`, `index*0x38 + [rdi+8]`) match byte for byte the old standalone function 0x5c25c90. The tool itself marked it as "one copy fewer". This is access to an element of a network vector (the neighboring function contains `m_ThreatLevelInfos` and `networkvar.h`). Now this code sits right next to the following function, and the tool merged them into one. 947 + 80 = 1027 bytes — exactly the new size. The logic did not change. Confidence is high.

<details><summary>What Opus corrected in Haiku's draft</summary>

- **Kez:** the draft assumed that the backstab angle or duration logic was simplified. In fact it is only a recompilation: the handle computation was moved into a function, the behavior is the same.
- **Legion Commander:** the draft stated that an "already received the effect" check was added. Such a check existed before; only the addition to the list was inlined.
- **Muerta:** the draft attributed the function to Double Shot and to a "replacement of the target handle hash". In fact it is the registration of a network field in the schema, which does not affect the game.
- **0x5c25d70:** the draft considered this a "fast path", and "field 0x61" and "size 0x38" new constants. In fact the function was merged with an existing 80-byte function; incidentally, 0x38 = 56, not 54.
- **Meepo:** the draft stated that the new function "replaces the zeroing of fields" and "possibly reinitializes properties". The main point was missed: the function removes `modifier_meepo_megameepo` from each clone and frees the list's memory. This is the only real change in behavior.
- It was not stated that there are no API changes at all, and that the differences in `ACT_*` constants are dumper noise.
