# Dota 6992: что изменилось

Отчёт создан автоматически 2026-11-23. Черновик по всем изменениям (частей: 1) — Claude Sonnet 5.5, проверка по исходным данным и итог — Claude Sonnet 5.5 (только с правом чтения); таблицы ниже посчитаны без модели.

## Сводка

### Главное

- **Новое предупреждение в GC-обработчике сообщений (libclient.so и libserver.so).** Конструктор протобуф-сообщения из пакета (`msgprotobuf.cpp`) для `gc_msg_src == 2` теперь пишет в лог GC строку `Message %s(%u) from %s claimed client_steam_id %s with gc_msg_src %d.`, если `client_steam_id` не совпал с уже записанным. Сообщение при этом не отбрасывается. Подробности в разделе «⚠ Ограничения и странное».
- **Заодно изменилась семантика для `gc_msg_src == 2`.** Раньше источник и steam_id записывались в сообщение, только если источник ещё не был задан (`+0x50 == 0`). Теперь для значения 2 они перезаписываются всегда.
- **Клиент: три функции списка экипировки на `C_DOTAPlayerController` и `C_DOTA_BaseNPC` теперь выходят сразу, если у глобального интерфейса слот vtable 42 (`+0x150`) возвращает `true`.** Что это за объект, из кода не определить. Связи с режимом кастомки нет (подробности в разделе «Клиент»).
- **API, консольные переменные и команды, схема, `.proto`, скрипты и Panorama не менялись.** Размер обеих библиотек почти тот же (код −512 байт у клиента и −640 у сервера), экспорт не изменился.

### ⚠ Ограничения и странное

**Сверка `client_steam_id` для GC-сообщений (libclient.so `0x7e66e40`, libserver.so `0x6bfa580`)**

- **Где.** Конструктор `CProtoBufMsg` из `IMsgNetPacket`. Его вызывает разбор пакета `0x7e64f00` для клиента. Новая строка есть в обеих библиотеках, а код дифф-функций совпадает.
- **Что делает новый код.**
  - Аргументы: `edx` — `gc_msg_src`, `rcx` — `client_steam_id`, `r8d` — доп. поле, которое пишется в `+0x6c`.
  - Если `gc_msg_src == 2`, а в сообщении уже есть источник (`+0x50 != 0`) и записанный steam_id (`+0x40`) отличается от переданного, функция пишет предупреждение.
  - Предупреждение идёт через `0x7e649c0` (обёртка над GC-логгером `GCHost::EmitBaseMessageV`). Форматы steam id — `[M:%u:%u:%u]`/`[C:%u:%u]`, имя типа сообщения берётся из `messagelist.cpp::GetMessage`. Константа `0x30` — это параметр вызова логгера. Что она значит, из кода не видно.
  - После лога выполнение идёт дальше, в ту же ветку, что и при совпадении. Значения `+0x40`, `+0x50`, `+0x6c` и флаги `|= 0x224` записываются. Отказа или выброса сообщения в этой функции нет.
- **Изменение поведения.** В старой версии эти поля записывались только при `+0x50 == 0`. В новой при `gc_msg_src == 2` они перезаписываются, даже если источник уже был задан. При остальных значениях `gc_msg_src` поведение прежнее.
- **Для кого.** Клиент и сервер, все игры. Это не специфика кастомок: сравнений с `m_iGameMode == 15` нет.
- **Что это значит.** Тот, кто собирает или пересылает GC-сообщения вручную (эмуляция GC, прокси), увидит предупреждение при расхождении steam_id. Блокировки в этом коде нет.
- **Надёжность.**
  - Логика функции прочитана по дизассемблеру, поэтому «только лог, без отказа» — надёжный вывод.
  - Что означает значение `gc_msg_src == 2` и какие вызывающие функции его передают, не установлено.
  - Основной путь разбора пакета (`0x7e64f00`) передаёт `gc_msg_src = 0` и `client_steam_id = 0`, то есть новая ветка на нём не срабатывает.

### Клиент (libclient.so)

**Сеть: GC-сообщения.** Описано в разделе «⚠».

**Список экипировки на сущностях (`0x579cb50`, `0x579d030`, `0x57cca20`)**

- **Что поменялось.** В начале каждой функции, после существующей проверки `[global]+0x58 != 0`, добавлен вызов виртуального метода `+0x150` (слот 42) у объекта из глобальной ячейки `0x98e7fb8`. Если он возвращает `true`, функция завершается без работы.
- **Что делают функции.**
  - `0x579cb50` вызывается из `C_DOTAPlayerController::vfunc#114`. Она пересобирает массив из `+0x1018/+0x1010/+0x1008` и заново создаёт записи с ключами `"model"`, `"skin"`, `"ItemData"`.
  - `0x579d030` вызывается из функции со строками `"isRespawn"` и `"OverrideWearableClass"`. Она убирает из массива последний элемент, чей идентификатор совпал.
  - `0x57cca20` вызывается из `C_DOTA_BaseNPC::vfunc#16`. Она добавляет элемент в массив с лимитом `<= 0x20`.
  - Всё это клиентский список экипировки (wearables) сущности.
- **Что это значит.**
  - Когда слот 42 возвращает `true`, клиент не обновляет этот список.
  - Тот же слот 42 вызывается и в `C_DOTAPlayerController::vfunc#114`. Там это уже было до обновления, а результат `true` выставляет флаг `+0xeec = 1`.
  - Что за объект в `0x98e7fb8` и когда метод возвращает `true`, из кода определить не удалось.
- **Надёжность.**
  - То, что вызов добавлен, надёжно.
  - Смысл условия неизвестен. Привязки к кастомкам нет: в этих функциях нет сравнений с режимом 15, и кастомки они не упоминают.

### Сервер и движок

- Технических изменений платформы нет.
- Серверная часть GC-конструктора изменилась так же, как клиентская (см. «⚠»).
- Остальные изменённые функции libserver.so — пересборка, шаблонные инстанции или игровой код.

### Схема и протоколы

- Новых и удалённых классов или полей платформы нет.
- `.proto`, скрипты и Panorama из VPK не менялись.

- Вывод «сообщения GC с чужим steam_id, возможно, отбрасываются» не подтвердился. Код только пишет предупреждение, а потом всё равно записывает значения.

- Три клиентские функции черновик описал верно. Я добавил, что слот 42 того же объекта уже использовался в `C_DOTAPlayerController::vfunc#114`, а условие остаётся неизвестным.
