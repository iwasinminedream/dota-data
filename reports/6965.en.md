# Dota 6965: What Changed

The report was generated automatically on 2026-10-20. The draft of all changes (1 part) was written by Claude Haiku 4.5; verification against the source data and the final version by Claude Opus 5.5 (both read-only); the tables below were calculated without a model.

## Summary

### Highlights

- This is a technical build (6965, build 26090992) with no gameplay changes. In `libserver.so`, one function out of 220000 changed, nothing was added or removed. The strings and exports are the same, code size +0 bytes. The other libraries, including `libclient.so`, did not change (`so-query libs`).
- The only real code change is bot AI for Sand King → Burrow Strike (`CDOTA_Bot_AbilityUsage_SandKing_BurrowStrike::vfunc#5`). The `burrow_width` value is now read with the integer special-value getter (the fractional part is discarded) instead of the float one. The resulting number is the same. But the debug warning `AlertSpecialValueFloatIntoInteger` ("Reading FIELD_FLOAT value … into an integer container … will cause truncation") goes away. Bot behavior is practically unchanged (details in the section "Game code changes").
- The new enum member `ACT_DOTA_CAST5_STATUE = 1801` in the Lua API is dumper noise, not a new feature (see below).

### New properties and methods: what they do

There are no genuinely new properties, events, methods, flags or behaviors in this build.

- **`ACT_DOTA_CAST5_STATUE` (GameActivity_t, 1801)** is not a new feature. What the conclusion is based on:
  - **It is not new.** In `files/changelogs/*.json` this activity is "added" and then disappears dozens of times (6715, 6718, 6730, 6733, 6750, 6758, 6761, 6763, 6789–6791, 6807, 6831, 6877, 6944…), and each time with a different value: 1794–1806. `ACT_DOTA_VOODOO_REST` and `ACT_DOTA_SPWN` behave the same way.
  - **Values are unstable within a single build.** According to `dump-noise.md`, two dumps of this same build differ in `cl_script_reload`: `ACT_DOTA_CAST5_STATUE` is 1801 and 1806 there, the number 1801 in the other dump is occupied by `ACT_DOTA_VOODOO_REST`, and `ACT_DOTA_SPWN` disappears entirely. All values above ~1779 for these activities get shuffled.
  - **Comparing the dumps confirms this.** The previous raw dump has `ACT_DOTA_SPWN = 1803` and `ACT_DOTA_VOODOO_REST = 1808`, but no `CAST5_STATUE`. In the current one it is the other way around.
  - **Conclusion.** Activity numbers from this range are apparently assigned at load time and are not constant. Confidence in this conclusion is high. Do not rely on the numbers 1792–1811 in custom games: use the constant name, not a literal.

### For custom game developers

- There are no changes in the Lua API, Panorama, events, modifiers or console variables. `api-changes.txt` contains only the noisy `ACT_DOTA_CAST5_STATUE` (see above).
- Existing addons are not at risk. There is one caveat: if code compares an activity to a numeric literal from the ~1780–1811 range (statues, `ACT_DOTA_RELAX_*`, `ACT_DOTA_RUN_ALT`, `ACT_DOTA_CAST_FENCE`, etc.), it could have broken before as well — the numbers float from build to build. In `files/vscripts/enums.json`, the only ones currently from this range are `ACT_DOTA_DEFEAT_STATUE` (1794), `ACT_DOTA_CHANNEL_STATUE` (1795) and `ACT_DOTA_CAST5_STATUE` (1801), so the list is incomplete.

### Game code changes

**`CDOTA_Bot_AbilityUsage_SandKing_BurrowStrike::vfunc#5`** (libserver.so, new address 0x5f3dd30, old 0x5f45910; 2099 → 2107 bytes, 469 → 471 instructions). This is bot logic: evaluating whether to use Burrow Strike and where.

- **What changed.** Right after reading `"burrow_width"`, a different special-value getter is called:
  - Before: `call 0x3a5fbf0`, the result is taken from `eax` (`mov r13d, eax`). This is the integer variant of the getter, used in about 551 places. Internally it computes a float, truncates it (`cvttss2si`) and, if the value is fractional, calls 0x3a5f890. That contains the alert `"AlertSpecialValueFloatIntoInteger"` with the text "CDOTABaseAbility: Reading FIELD_FLOAT value for '%s' into an integer container for ability '%s', will cause truncation." (the text is assembled from `movabs` constants).
  - After: `call 0x3a5f0a0`, the result is taken from `xmm0` (`movd r15d, xmm0`). This is the float variant of the getter, about 575 places. Then comes an explicit truncation `cvttss2si eax, xmm6` before passing it on.
  - The remaining differences are register changes (r13/r14/r15) and instruction order, i.e. recompilation.
- **Where the value is passed.** The width goes as a stack argument into the shared function 0x5ef4fa0. This is the bots' search for the best line for line-based attacks; it is also called by Jakiro Dual Breath / Ice Path / Macropyre, Earthshaker Fissure and Windrunner Powershot. Inside, the argument is squared (`imul r14d, r14d`) and compared with the squared distances to targets.
- **Constants.** Unchanged: 200 (addition to cast range), 1000, 0.75, 100.
- **Cross-check with KV.** In `files/abilities.json`, `sandking_burrowstrike` has `burrow_width = 150` with `affected_by_aoe_increase: 1`. With a radius bonus the width can become fractional — in that case the old code would trigger the alert.
- **What this means in the game.** The width is computed the same way for bots (truncation in both cases), only the false warning disappears. It does not affect players or custom games.
- **Confidence.** High for the fact of the getter replacement and its consequences: verified via `func old/new` of both getters and the called function. What exactly Valve wanted to fix is not visible from the code — presumably the warning with AoE bonuses.
