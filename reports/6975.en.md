# Dota 6975: what changed

The report was generated automatically on 2026-11-13. The draft covering all changes (1 part) was written by Claude Haiku 4.5; verification against the source data and the final version are by Claude Opus 5.5 (both read-only). The tables below were computed without a model.

## Summary

### Highlights

- **New player report category: "Bot" (Botting).** Two localization strings were added: `DOTA_PlayerReportPopup_Botting_Title` ("Botting", "Бот" in the Russian localization) and `DOTA_PlayerReportPopup_Botting_Tooltip` ("Their hero is being played by automated software instead of a person.", in Russian "Этим героем управляет автоматизированная программа, а не человек."). The strings `BottingButton` and `#DOTA_PlayerReportPopup_Botting_Title` appeared in libclient.so.
- **The report window `CDOTA_DB_Popup_ReportPlayerNew` got a seventh negative-category button.** There used to be six: ToxicText, ToxicVoice, EnemySmurfing, Griefing, EnemyCheating, DidNotPlayRole. The window object grew from 0xf0 to 0xf8 bytes, and the shared category-button update loop now walks 7 buttons instead of 6.
- **The "Botting" reason can now be shown in the list of successful reports.** The "reason number → title" function got a new branch. The number of reasons (0…13) did not change: the value apparently already existed in the enumeration but had no title.
- **Game logic did not change.** In libserver.so, 0 functions, 0 strings and 0 exports changed. The Lua API, Panorama API, events and modifiers did not change either: api-changes.txt contains only the two localization strings.
- The remaining changes in libclient.so are recompilation effects: a shift of jump tables, a different compiler inlining decision, and two functions merged by the analyzer.

### New properties and methods: what they do

There are no new properties, events or methods in the Lua API or Panorama in this build. api-changes.txt contains only localization, so there is nothing to check with HasFunction.

- `BottingButton` is not an API. It is a panel identifier in Valve's layout `file://{resources}/layout/popups/popup_report_player_new.xml`. The report window constructor (0x681a480) looks it up by name, checks its type and stores the pointer in a new object field at +0xf0. Basis: the string next to the other category buttons (so-query context) and the constructor code (fdiff). Confidence is high. It has no significance for custom games.
- In Haiku's draft, the "methods" vfunc#51/#9/#61/#58 were listed under "API". These are not new methods but virtual calls of the Panorama engine: looking up a child panel by name and checking its type. The constructor simply repeats them for the new button. Nothing was added to the API.

### For custom game developers

- There are no changes to the Lua API (vscripts), Panorama API, game events, modifiers or console variables. Existing addons are not at risk.
- The new localization keys `DOTA_PlayerReportPopup_Botting_Title` and `DOTA_PlayerReportPopup_Botting_Tooltip` exist in all languages (checked, for example, in russian, ukrainian, latam, turkish). This is main-game UI and does not concern custom games.
- The numbers of dynamic activities in `cl_script_reload` (`ACT_DOTA_CAST5_STATUE`, `ACT_DOTA_VOODOO_REST`, `ACT_DOTA_CYCLONE`, `ACT_DOTA_TORRENT`, `muerta_debut_satyr_*`, etc.) differ even between two dumps of the same build (dump-noise.md). For example, `ACT_DOTA_CAST5_STATUE` was 1801 in the previous dump and became 1804 in the current one. This is not a game change, but the takeaway is: the numeric values of these ACT_* constants must not be hardcoded; refer to them by name.

### Changes in game code

In total 19 functions changed, all in libclient.so; there are no changes in libserver.so.

**Player report window (8 functions)**

- **0x681a480 — constructor of `CDOTA_DB_Popup_ReportPlayerNew`.** It is called right after `operator new(0xf8)`: in 0x71c3640 (from the scoreboard, `dota_hud_scoreboard_player.xml`) and in 0x6570340.
  - After the last old button is saved in `[this+0xe8]`, a lookup of the `"BottingButton"` panel, a check of its type and a write to `[this+0xf0]` were added.
  - Three branches of the cast error message were also added: `"Attempted to cast panel '%s' to type '%s'"`, `"!pPanel || pResult"`, and the constant 0x5b2 — probably a source line number. This is service code for the check, inlined together with the panel lookup.
  - There are no new conditions for other categories.
  - Basis: the full fdiff, context. Confidence is high.
- **Window object size 0xf0 → 0xf8.** Four functions change because of this:
  - 0x71c3640 (`"OverwatchReport"`; called from a player row on the scoreboard) — `operator new(0xf8)` and then the constructor;
  - 0x6570340 — `operator new(0xf8)`; it is called by the match summary page (`dashboard_page_post_game_overview_*`), meaning the report can also be opened after the game;
  - 0x6807b30 `CDOTA_DB_Popup_ReportPlayerNew::vfunc#63` — the destructor: a call to the destructor of the base `CUI_Popup` and freeing of 0xf8 bytes;
  - 0x6807c90 — the same size on freeing.

  This is not a "field offset" and not an "8-byte storage structure", as Haiku wrote: one new panel pointer appeared. Confidence is high.
- **0x6837d70 `CDOTA_DB_Popup_ReportPlayerNew::vfunc#57` — category selection handling** (`"Report_AnyCategorySelected"`, `"reason"`, `"OverwatchApplicableReport"`).
  - The loop over category buttons `[this+0xc0 … +0xf0)` now runs up to `+0xf8`, so the Botting button gets the same `reason` update as the others.
  - The "report is suitable for Overwatch" check did not change: among the selected categories, type 5 or 6 is searched for (`sub edx,5; cmp dl,1`).
  - A flag was moved from register r15 to a stack variable — this is register reallocation, not a new flag.
  - Whether Botting is among the Overwatch categories cannot be determined from this code: the category types come from data filled in elsewhere.
  - Confidence is high for the loop extension; for Overwatch the conclusion is unclear.
- **0x5bc7940 — the function "reason number → `#DOTA_PlayerReportPopup_*_Title`".** It is called by 0x67e5710 (`"SuccessfulReportSnippet"`, `"successful_report_reason"`, `"NoSuccessfulReports"`) — the list of successful reports.
  - The bound `cmp edi, 0xd` stayed the same; a branch for `#DOTA_PlayerReportPopup_Botting_Title` was added. This means that one reason number, which previously yielded the default value, now gets the "Botting" title.
  - The swap of `GoodTeamwork`/`ToxicVoice` in the diff is a different layout of branches in the code, not a new category order (Haiku's mistake).
  - Confidence is high for the new branch. The reason number itself has not been determined.
- **0x682eb70 — the short film voting window (`popup_short_film_workshop_vote.xml`).** The lookup and check of one of the panels (before `NextButton`) used to be inlined into the function; now it is a call to the shared function 0x6806010. That is why the cast error strings and virtual calls "disappeared". Behavior is the same; this is a compiler decision. The code did not "move" to the report window, as Haiku assumed. Confidence is high.

**Recompilation, not logic (11 functions)**

- **Shift of `switch` jump tables in .rodata by 0x100 bytes (10 functions):** 0x3ab8100 (fields `m_CoverImage`, `m_URLForImages`…), 0x3afbfb0 `C_DynamicPropClientFadeOut::vfunc#10`, 0x3afc8a0, 0x3b3c0d0 `CPointClientUIWorldTextPanelPreviewer::vfunc#2`, 0x3b4cc90, 0x3b4f100, 0x3b4f340, 0x3b4f580, 0x3b8edb0 `CNetworkTransmitComponent::vfunc#3`, 0x3bd0e00.
  - In all of them only the table address after `cmp …, 6; ja` changed. The analyzer shows it as "strings" like `"uQl"→"uRl"`, `"1ip"→"1jp"`. The number of instructions did not change.
  - This is a consequence of the two new strings in .rodata. Confidence is high.
- **0x5bca8d0 — functions merged by the analyzer.**
  - The new "35 lines at the start" are the getter of a static object created on first access (flag check, `__cxa_guard_acquire`, constructor 0x5bca7a0, `__cxa_atexit`, `__cxa_guard_release`).
  - In the old build it was a separate function 0x5bca7b0 with `int3` padding after it. In the new one, the next function begins right after `ret` (0x5bca940), and the analyzer merged them. Hence "functions 280912 → 280911" and "one copy fewer: 0x5bca7b0".
  - The logic did not change (disasm old/new). Confidence is high.
