## Summary

### Key points

- **Aghanim's Shard: the item that granted the modifier can no longer be sold until it is removed.** This is the only logic change in the update. A new block appeared in `CDOTA_Modifier_Aghanims_Shard::OnCreated`. The modifier finds the item from the `source_item` parameter, sets its `m_bForceUnsellable = true` and clears `m_bMarkForSell` (the "sell" mark). Both fields are replicated to clients. The item itself, as before, is removed in the first `OnIntervalThink`. This most likely closes the window between receiving the buff and the item being removed, during which the item could be sold. Confidence: code and field names — high; that this is a sell fix — medium (inferred from the code logic, there are no patch notes).
- The other 5 changed libserver.so functions are recompilations with no logic change. The compiler inlined the entity lookup by handle, switched the called copy of the ability value getter, and folded a constant hash. They affect Chipped Vest, the handler with the Silver Edge debuff, Arcane Blink, Bottomless Chalice and the Shard's `OnIntervalThink`.
- One function was removed and one was added. They are the same entity initialization: previously the network field change notification was inlined into it, now it goes through a virtual call.
- libclient.so did not change: 0 changed functions, code +0 bytes.
- The Lua/Panorama API did not change. The dump only gained three localization strings `DOTA_Item_Temptool_18/19/20` — placeholders with no items.

### Changes in game code

6 functions in libserver.so changed, one more was added and one removed. libclient.so has no changes. Everything was analyzed.

**1. `CDOTA_Modifier_Aghanims_Shard::OnCreated` (0x4d43890 → 0x4d488e0) — new logic.**

What was and remains:
- the modifier reads `"source_item"` and stores the item handle in the field 0x1aa8 (or −1 if there is no source);
- then come the previous actions: `"tormentor"`, iterating over abilities, the particle `particles/items_fx/aghanims_shard.vpcf`, the event `"shard_acquired"`.

What was added: after the handle is stored, the modifier obtains the item entity and, if it exists, does the following.
- If `byte [item+0x878] == 0`: adds offset 0x878 to the list of changed fields, calls virtual slot 29 (network notification of a field change) and writes 1.
- If `byte [item+0x8f1] != 0`: the same for offset 0x8f1, writes 0.

How the fields were identified — from the network field table of `CDOTA_Item` (function 0x5a11510, "name → offset" registration):
- 0x876 — `m_bSellable`, 0x877 — `m_bInitiallySellable`, **0x878 — `m_bForceUnsellable`**;
- 0x8f0 — `m_bCombineLocked`, **0x8f1 — `m_bMarkForSell`**;
- in the previous build `m_bMarkForSell` is also at 0x8f1 (xref old), the field layout did not change.

How the removal works:
- `OnCreated` ends by starting the interval (tail call 0x4e39c40 with 0, by context — `StartIntervalThink(0)`);
- `OnIntervalThink` calls the same function with −1, i.e. stops the interval, and passes the item to 0x5993c10.
- 0x5993c10 is called by the Aegis removal and by `CDOTA_Item_ChainMail::OnSpellStart` (Chain Mail absorption). Judging by these callers, it is probably entity removal, i.e. the item is destroyed.

Meaning: in the interval between the buff being granted and the item being removed, the item can no longer be sold — neither directly nor via the sell mark. In the KV, `item_aghanims_shard` has passive behavior and no `ItemSellable` flag, i.e. by default the item is sellable. `item_aghanims_shard_roshan` already had `ItemSellable 0` before.

Confidence:
- the code itself and the field names — high;
- that this is protection against selling the Shard after receiving the buff — medium;
- that 0x5993c10 removes the item — medium-high (from the callers).

**2. Inlining of the entity lookup by handle — no logic change (3 functions):**
- `CDOTA_Modifier_Aghanims_Shard::OnIntervalThink` (0x4d425e0): the source item handle in field 0x1aa8;
- function 0x4d42940, called from `CDOTA_Modifier_Item_Chipped_Vest::vfunc#95`: handle in field 0xcc;
- function 0x4d435d0 with the strings `"modifier_silver_edge_debuff"`, `"duration"`, `"DOTA_Item.SilverEdge.Target"`, called from `CDOTA_Modifier_Item_Caster_Rapier::vfunc#95`: handle in field 0xd0.

Why this is not logic:
- Previously the functions called 0x3a3fe70 — a generic entity lookup by handle with 2192 callers. Now its body is inlined one to one: the check for −1/−2, the index `& 0x7fff`, the block `>> 9 & 0x3f`, the cell `& 0x1ff` of size 0x70, the serial number comparison at +0x10.
- `cmp rax, rdi` → `cmp rdi, rax` before `jne` — an equality check, the operand order does not matter.
- `vfunc#95` is not item logic: it is a function that only writes handler pointers into object fields. Which callback exactly is function 0x4d435d0 was not established from the code.

Confidence: high.

**3. `CDOTA_Modifier_Item_Arcane_Blink_Buff::OnCreated` (0x4d47b30 → 0x4d48780) — recompilation.**
- Previously `cast_pct_improvement` was read through the wrapper 0x4383500: a NULL check on the ability, a call to 0x43830c0, and writing the result into the field.
- Now the generic function 0x3a5fbf0 is called with the arguments "current level (−1), flags 0": the NULL check is inlined, the result is written to 0x1aa8.
- Both functions are the same integer ability value getter: the same path through `AbilityValueData`, the same special cases `AbilityManaCost`/`AbilityHealthCost`. 0x43830c0 is a copy of the generic getter specialized for particular arguments.
- `manacost_reduction`, `debuff_amp`, `cast_range_bonus` are read as before. The numbers did not change: there are no ability value constants in the diff.

Confidence: high.

**4. Registration of the network variable `CDOTA_Item_Bottomless_Chalice::m_iStoredRuneType` with the callback `OnChaliceStoredRuneChanged` (0x4d4dfe0) — recompilation.**
- One step `call F; lea rdi,[rbx+4]; mov esi,eax` disappeared from the field name hashing chain (seed 0x31415937). The compiler computed it at build time.
- The function size is the same (3179 bytes), no logic.

Confidence: high.

**5. 0x4d48dc0 (570 bytes) removed and 0x4d496d0 (225 bytes) added — the same function.**
- Both:
  - call the base constructor (0x59bc860 / 0x59bc920);
  - write the virtual function table;
  - zero the fields 0x934 and 0x938, notify the network of the change of field 0x934, then set 0x934 = −1.
- Difference: the old version contained an inlined `CNetworkTransmitComponent::StateChanged` with a debug string. The new one calls `CBaseEntity::vfunc#29` — the same virtual slot 29 as in the new Shard code.
- The string `"CNetworkTransmitComponent::StateChanged(%s) @%s:%d"` did not disappear from the library (strings +0 −0). It is used in other functions, for example in 0x57536e0, which is called by the Shard's `OnCreated`.
- Whose class this is was not established.
- The pair of "copies of existing code" (0x4d49150 → 0x4d49910, 118 bytes) is a caller of this same function, not new code.

Confidence: high.
