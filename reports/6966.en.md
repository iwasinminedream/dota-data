# Dota 6966: what changed

The report was generated automatically on 2026-10-22. The draft of all changes (1 part) was written by Claude Haiku 4.5, and the check against the source data and the final version by Claude Opus 5.5 (both read-only). The tables below were calculated without a model.

## Summary

### Highlights

- This is a small server-side update (6965 → 6966). The Lua API, Panorama and events did not change: `api-changes.txt` is empty. Not a single function changed in libclient.so. In libserver.so, 6 functions out of 220000 changed, with none added or removed, and the strings and exports are the same (+0/−0). The code became 64 bytes shorter.
- The logic really changed only for Megameepo (`meepo_megameepo`). It looks like a bug fix: the game now removes the projectiles of Meepos that are still in flight and zeroes the ability's internal counters:
  - at the start of each cast (`OnSpellStart`);
  - when `modifier_meepo_megameepo_self` is removed, that is, when the Megameepo form ends (`OnDestroy`);
  - in the unnamed virtual slot of the ability, `vfunc#365`.
  
  Previously, projectiles in flight stayed, and the counter of mounted Meepos was not reset after the form ended.
- The other three changed functions (Kez's "Katana" shard, Legion Commander `Press The Attack`, Ogre Magi `Fire Shield`/Smash) are only recompilation: the compiler inlined helper functions differently, and behavior did not change.
- Ability values, tooltips, texts and new mechanics are not visible in this update.

### New properties and methods: what they do

None. `api-changes.txt` is empty. No new strings or exported symbols appeared in the .so files (so-diff: "strings +0 −0, exports +0 −0"). There are no new or removed functions in either libserver.so or libclient.so.

### For custom game developers

- The Lua API, Panorama, game events, modifiers and console variables did not change. This update should not break existing addons.
- The numbers of the `ACT_DOTA_*` constants in the dump "float" (`ACT_DOTA_CYCLONE`, `ACT_DOTA_IMPALE`, `ACT_DOTA_RUN_ALT`, etc.), and `ACT_DOTA_SPWN` and `ACT_DOTA_TORRENT` appear and disappear. This is dumper noise: two dumps of the same build differ (`dump-noise.md`, section `cl_script_reload`). It is not a game change. Practical takeaway: in code it is better to refer to activities by constant name rather than by number.
- If a custom game uses the original `meepo_megameepo`, Meepos flying to the shoulders now disappear together with their projectiles when the form ends or the ability is cast again (details below). If Megameepo is implemented in Lua, nothing changes.

### Changes in game code

All 6 changed functions are in libserver.so. The analysis was done as follows: I looked at the whole diff (`fdiff`), the code of the old and new versions (`func old/new`) and the called functions.

**Megameepo (`CDOTA_Ability_Meepo_MegaMeepo`): a real logic change**

First, what the ability's fields store. This can be seen from the projectile hit handler `vfunc#371` (0x4a7b750, strings `"meepo_count"`, `"previous_meepo"`, `"source_meepo"`):
- `+0x880/+0x888` is the list of indices of Meepo projectiles that are still flying toward the main Meepo. `OnSpellStart` adds the `proj_index` value to it, and `vfunc#371` removes the index when the projectile has arrived.
- `+0x868/+0x870` is the list of handles of Meepos already sitting on the shoulders. On mounting, a Meepo is added to it, and its size is passed to `modifier_meepo_megameepo` as `"meepo_count"`.

The new call in all three functions is `0x5b86a80` with the global object `0x83ff380`. `OnSpellStart` passes this same object to the projectile creation function `0x5c293c0`, which returns `proj_index`, so this is a projectile manager. The function `0x5b86a80` walks its list and removes and frees all projectiles whose source ability is this one. It was previously also called by `HurlBoulder` (Brewmaster and Mud Golem) in slot `vfunc#15` and by `vfunc#365` itself.

1. **`CDOTA_Modifier_Meepo_MegaMeepo_Self::OnDestroy`** (0x4a74810 → 0x4a75450): fires when the Megameepo form ends.
   - Before: the mounted Meepos were removed one by one (call to `0x4a12a50`), but the ability's counters were not reset, and projectiles in flight were not removed.
   - After: once all Meepos are removed, and also immediately if there were none, `0x5b86a80(projectile manager, ability)` is called, then `[+0x868] = 0` and `[+0x880] = 0`.
   - In game: when the form ends, Meepos still flying toward the main Meepo will no longer arrive and "mount" onto it after the form has ended.
   - Confidence: for what exactly is done in the code, high. For which in-game bug this corresponds to, medium; this is an inference from the logic, and there is no confirmation in the patch notes.
2. **`CDOTA_Ability_Meepo_MegaMeepo::OnSpellStart`** (0x4a65240 → 0x4a652a0).
   - Zeroing `+0x868`/`+0x880` at the start existed before. What is new: `0x5b86a80` is called before it, so the projectiles of the previous cast are destroyed. Previously the lists were simply zeroed, and old projectiles could remain in flight.
   - The rest of the function's logic did not change: the `npc_dota_meepo_megameepo_frame` frame, the search for Meepos within `radius`, the exceptions for `modifier_faceless_void_chronosphere_freeze`, `modifier_enigma_black_hole_pull`, `modifier_legion_commander_duel`, and the projectile with `modifier_meepo_flung`.
   - Confidence: high.
3. **`CDOTA_Ability_Meepo_MegaMeepo::vfunc#365`** (0x499e9a0).
   - An unnamed slot. It removes `modifier_meepo_megameepo_self` from the owner and calls `0x5b86a80`. Previously only `+0x880` was reset; now `+0x868` is too, so the counter of mounted Meepos is also zeroed.
   - When the engine calls this slot cannot be determined from the code: there are no direct calls, only via the vtable. Confidence in what the code does: high.

The ability constants did not change, so there is nothing to check against KV. The description `DOTA_Tooltip_ability_meepo_megameepo` in the localization ("mounts all other Meepos in a %radius% radius") is consistent with the purpose of these lists.

**Recompilation without behavior change**

4. **Kez shard, katana strike** (0x4a4b130, unnamed; called from 0x4a5ce60 — `kez_switch_weapons`/`modifier_kez_katana_shard_debuff`; strings `"backstab_angle"`, `"stun_duration"`, `modifier_kez_katana_shard_active`).
   - Before, the caster's handle was obtained by calling `0x49aaca0` (entity → CHandle, with a null check). Now the same code is inlined directly into the function: this is where the "new" constants `0x7fff`, `0xf` and `−1` in the summary come from.
   - The old and new versions of `0x49aaca0`/`0x49aacb0` are byte-for-byte identical. The backstab, durations and event `0xd1` did not change.
   - Confidence: high.
5. **`CDOTA_Ability_Legion_Commander_PressTheAttack::OnSpellStart`** (0x4a7b670 → 0x4a6d9f0).
   - Adding the target and caster handles to the allies list was previously inlined in the function. Now a separate function `0x4a6b7b0` is called: this is `CUtlVector::AddToTail`, and 5 more abilities call it.
   - Hence the "−1 −1 −1 −1" in the summary (the `add …, 1` moved into this function).
   - The checks, radius, search flags (`0x13`), particle and sound are the same. Confidence: high.
6. **`CDOTA_Ability_Ogre_Magi_Smash::OnSpellStart`** (0x4a7bce0 → 0x4a6b820).
   - The same thing: the inlined addition of the caster's handle to the targets list is replaced by a call to `0x4a6b7b0`, and the rest is a rearrangement of stack slots.
   - The merge order of the three target lists, multicast (`ogre_magi_multicast`, `multicast_fireshield_aoe`), `modifier_ogre_magi_smash_buff` and the sounds did not change. Confidence: high.

Why the neighboring functions were recompiled: the addresses of Legion, Ogre and the Meepo modifier shifted into one region (0x4a6b…–0x4a75…). They are probably in the same compilation unit as Megameepo, and an edit in it changed the inlining in its neighbors. This is an assumption.
